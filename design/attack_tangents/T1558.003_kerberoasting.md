# T1558.003 — Kerberoasting

> Seed entry for the [attack-tangents catalog](README.md). Content is the tangent walk from the
> chain-checker session (`detection/chain.py`), grounded against the local ATT&CK bundle and Sigma corpus.

## Summary

Kerberoasting abuses a normal Kerberos feature: **any authenticated domain user can request a service
ticket (TGS, event 4769) for any account that has an SPN** (Service Principal Name). The TGS is encrypted
with the *service account's* password-derived key, so an attacker requests tickets for SPN-bearing
accounts, exports the ticket material, and **cracks it offline** — no further interaction with the domain,
nothing to detect on the wire after the request. It works because service-account passwords are often
human-set and weak. It only works on **user** service accounts: machine-account passwords are 120-char
random and effectively uncrackable.

The detection-relevant fact: the *malicious* part (the cracking) happens **off-system**. On the wire you
only see the ticket *request*. So detection is about recognizing an abnormal *request pattern*, then
catching the *consequence* (the cracked account being used) downstream — which is why this is a kill-chain
problem, not a single-event one.

## Variant tree (the tangents)

- **Classic RC4 kerberoast.** Request the TGS with **RC4-HMAC** encryption (`0x17`). RC4-TGS hashes crack
  fast (hashcat mode 13100 — essentially the NTLM hash). This is the loud, classic signature: requesting
  RC4 when the domain supports AES is itself a *deliberate downgrade* and suspicious on its own.
- **AES kerberoast (evasion).** As defenders flag RC4 requests, sophisticated attackers request **AES**
  tickets (`0x11`/`0x12`) and crack the AES256 TGS-REP hashes offline (hashcat 19700) on a **purpose-built
  GPU rig**. Slower per hash, very feasible for weak/medium passwords. *Defeats any RC4-keyed detector* —
  the encryption-agnostic signal is the fan-out, not the cipher.
- **Targeted kerberoast (stealth).** Request a ticket for **one** specific high-value SPN — no RC4, no
  burst. Defeats *both* the RC4 filter *and* the fan-out atom. The only signal left is **novelty/rarity**:
  an account requesting a ticket for an SPN it has never touched, or for a high-value service account.
- **Adjacent / cross-tagged.** Our corpus tags T1558.003 onto **CVE-2021-42278/42287** (sAMAccountName
  spoofing → "noPac") and **KrbRelay / KrbRelayUp / RemoteKrbRelay**. These are *different* techniques that
  share the Kerberos surface — a mapping-precision tangent (see [[project_skos_graded_mapping_seam]]): the
  tag is a lossy claim, and "what the rule detects" should be judged by content, not the tag string.

## Telemetry

- **Required for the request signal:** event **4769** (TGS request) with `Service_Name` (the SPN target),
  `Ticket_Encryption_Type` (RC4 vs AES), `Account_Name` (requester), and ideally `Ticket_Options` (the
  KDC-option bitmask). Without `Service_Name` + `Ticket_Encryption_Type` there is **no kerberoast signal**.
- **For the chain consequence:** **4624** (logon) with `LogonType`, `Computer_Name` — to catch the cracked
  service account being *used* against a crown-jewel host.
- **Context:** **4768** (TGT request) anchors the actor's session start; **process telemetry**
  (Sysmon/4688) catches the *tool* (Rubeus.exe, Impacket GetUserSPNs) where available.
- **Nice-to-have:** TGT:TGS ratio needs both 4768 and 4769 for the same account.

## Detection signals + fidelity (graded, additive — none is a hard gate)

- **SPN-ticket fan-out** — `4769` distinct `Service_Name` count / window — fidelity **MEDIUM–HIGH** —
  the *encryption-agnostic core* signal; this is what survives the AES variant. Benign service-discovery
  tools can also fan out → discrimination needs **baseline-for-this-account** (data-gated).
- **RC4 downgrade** — `Ticket_Encryption_Type == 0x17` when AES is available — fidelity **MEDIUM
  (booster)** — high-precision *when present* (RC4 is abnormal; AES is the default), but **absent in the
  AES variant**. This is the signal our chain S1 currently keys on. It was doing precision work *for free*;
  drop it as a gate and a benign high-fan-out account becomes an FP.
- **Ticket-options fingerprint** — `Ticket_Options` bitmask — fidelity **LOW–MEDIUM** — the KDC-option
  flags fingerprint the *requesting library* (Rubeus vs Impacket vs native client). Tool/version-dependent
  → a corpus question, not a constant.
- **User-SPN targeting** — SPN belongs to a *user* service account, not a machine account — **refiner** —
  drops machine-account noise (uncrackable), doesn't fire on its own.
- **Honeypot SPN** — any 4769 for a planted decoy service account — fidelity **VERY HIGH (near-
  deterministic)** — *any* request is malicious. The highest-fidelity signal available and the cheapest to
  deploy; needs nothing but a planted account.
- **Tool execution** — Rubeus.exe / GetUserSPNs / suspicious PowerShell ticket request — fidelity
  **HIGH** — needs process telemetry. **12 of our 17 Sigma claims key here** (HackTool-Rubeus,
  ticket-request-via-PowerShell/CLI, SPN-enumeration-via-setspn), *not* on 4769 content.
- **TGT:TGS ratio** — one 4768 → many 4769 for one account — fidelity **LOW–MEDIUM** — statistical tell,
  weak alone.

The structural point: **a stage is a constellation of signals at different fidelities, summed** — not a
boolean. Detection is fractal: chain-completeness × stage-confidence × signal-fidelity, additive at every
level. The current chain checker's `rc4_fanout` is the *boolean* simplification of this stage.

## Evasions

- **Switch to AES** — defeats RC4-keyed detection (the main one in the wild). Forces reliance on the
  fan-out + baseline signals.
- **Go targeted** — one ticket, no burst — defeats both RC4 and fan-out; only novelty/rarity remains.
- **Throttle** — spread requests across a long window to slip the fan-out threshold.
- **Shadow of an absent control.** Kerberoasting is, in part, the shadow of weak service-account password
  policy and the absence of **gMSA / Managed Service Accounts** (which give 120-char machine-managed
  passwords). Where gMSA is deployed, the crackable surface largely disappears — the detection exists
  because a preventive control is missing or partial (cf. [[project_lsass_cell_coverage_correction]]'s
  "detection = shadow of an absent/bypassable control").

## Kill-chain / cross-actor structure

Kerberoast is a *segment* in a credential-access → lateral-movement path, and its defining feature is an
**identity pivot**:

1. Account **A** (foothold) requests an RC4/AES TGS for SPN `MSSQLSvc/sqlserver` — the roast.
2. The attacker cracks `svc_sql`'s password **offline** — *no events*.
3. The attacker logs in **as `svc_sql`** to the crown-jewel host — a *different account* than A.

So the chain spans two identities, joined by **SPN → service-account**. The current `check_chain` is
*per-actor* (groups by `Account_Name`), so it can only express the *relaxed* "same account roasts then
pivots" version — it **cannot** express the realistic cross-actor join. That join (`roast(A, SPN) ∧
spn_account(SPN, Svc) ∧ sensitive_logon(Svc, Host) ∧ after`) is a **relational join across identities** —
the attack-graph / Datalog view, not a per-actor scan. This is the deferred "cross-actor linkage" rung and
the reason kill-chain detection is really a *path over an identity graph*, not per-actor path analysis.

## Data availability — the honest wall

**We cannot test the request-side signal locally.** Verified 2026-06-24:

- **bots-v3** Windows log is a stripped digest — **zero 4768/4769**, fields cut to
  `accountName/computer/logonType/processName`. No `Service_Name`, no `Ticket_Encryption_Type`. The raw
  `botsv3.tgz` (1.1G) *may* carry full 4769s but is locked in Splunk `journal.gz` index format (needs a
  decoder).
- **OTRF** local copy is only the LSASS credential-dumping cell (T1003.001) — no kerberoast capture.
- **faker-kerberos v2** (synthetic) proved the chain *mechanism* (conjunction load-bearing, ordering
  works) but **cannot earn fidelity** — author-both-sides circularity (we wrote the attack and the
  detector). Only RC4 + normal ticket-options modeled; can't test AES, targeted, ticket-options, or
  honeypot variants as-is.

So the request-side signals above are **specified, not validated.** The unlock is a real capture with
4769 SPN/encryption fields (decode `botsv3.tgz`, or pull an OTRF/attack_data kerberoast set).
