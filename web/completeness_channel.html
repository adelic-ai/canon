The completeness channel — missing fields as a third axis

An absence is two claims, not one: does it break the detection, and — separately — why is it gone?

canon · design conversation · 2026-06-12 · extends the validity fold · designed, not built

Beyond "is this event malicious" and "what's the detection-relevant context," there is a third axis hiding in every log: telemetry completeness. A missing field raises a question that is mostly not a security question — and the discipline is to keep the two questions on separate channels so neither contaminates the other.

An absence is two independent readings

For any absent field, ask two things — and never conflate them:

1 · does it affect THIS detection?

Only if the field is on this event-type's benignity checklist. If yes → the ∀-validation can't close → the verdict is capped at NONE ("can't confirm context correct"). If no → the detection is simply unaffected. Most missing fields fall here.

2 · why is it absent?

A separate verdict, on a benign↔problematic spectrum, and usually an ops / pipeline concern, not a security one. It has its own value and its own owner — and it's orthogonal to the detection.

A field can be detection-irrelevant yet its absence still worth explaining; a field can be detection-relevant and its absence both cap the verdict and demand the "why." Two axes.

Validity splits — and the split is detection-relative

Canon's validity (well-formedness) fold currently treats a malformed-or-missing field as one thing. In the detection-finding context it should bifurcate by relevance to the finding being computed:

validity outcomewhere it goes
necessary for this finding a security-relevant input failure → caps the detection ∀ → carried in the verdict as the reason for NONE.
not necessary for this finding a data-quality signal → the health / ops channel, never the security verdict.
The split is not absolute — necessity is detection-relative. The same field is "necessary" for one detection and "not necessary" for another. So validity isn't partitioned once; it is projected through each finding's input-checklist into two streams. The checklist is set by the event type (which is why the eventID leads — it defines what "complete enough" means here).

The "why" spectrum — mostly ops, occasionally security

This is the validity fold's own honesty extended from malformed to missing: the same three indistinguishable causes (innocent / pipeline / the anomaly itself), spread on a spectrum.

transient · benign      network noise, a dropped event, a collection buffer overrun     → ops noise
persistent · benign     this sensor / OS / config never populates this field            → known gap, baseline it
problematic · unrelated  a misconfigured forwarder, failing disk, clock skew             → an IT/ops problem — flag it, but not THIS attack
problematic · relevant   attacker cleared the log / disabled the sensor / the gap IS       → now the absence is security evidence
                        the technique's footprint

Only the last row (and sometimes the third, via correlation) feeds back into the security verdict. The rest belong to the parallel health stream.

The verdict carries its own gaps (analyst awareness)

"NONE carries what was missing" applied to the human-facing output: a finding should carry a completeness manifest — not because an analyst couldn't look at the log themselves, but so the gap is explicit and unmissable, and nobody silently assumes the context was complete.

completeness manifest  (per finding)
  expected   : [ fields this event-type × source should carry ]
  present    : [ … ]
  absent
    necessary     : GrantedAccess   → capped verdict to NONE; would have closed "lsass read benign?"
    not-necessary : IntegrityLevel, Hashes.MD5   → health channel (see routing below)

When a finding is elevated to a human, the manifest travels with it: here is what we could not see, and here is what it would have told us. The deterministic field→clause renderer already does this for the other folds; the absent-necessary list is just one more honest clause.

Routing the non-relevant gaps — an ops W→route, node-dependent

The detection-irrelevant absences are real work for someone — just not the security analyst. Which team owns a gap is a function of (cause × node):

causeowner
misconfigured forwarder / normalization bugplatform / detection-engineering
sensor broken on a specific hostendpoint / EDR team or host owner
network dropsnetwork / infra
Deferred component (forward). This is the same shape as detection's W→technique routing, pointed at ops: route (cause, node) → responsible team, the way detection routes (W, type) → verifier. The node-dependence is the key wrinkle the user flagged — the same missing field routes differently on a domain controller, a workstation, a cloud asset — so the router's input is the asset / ownership graph (the environment graph from scaling the loop). Same machinery, ops target. Not built.

What the completeness fold needs

  • An expected-completeness model, per (event-type × source × config) — "what fields should this event carry here?" Without it you can't tell expected-absent (legit) from unexpectedly-absent (worth explaining). OCSF's required / recommended / optional markings give a class-level floor; the rest is an environment baseline, learned like the behavioral one.
  • Aggregation, not per-event alerting, on the health channel. Most absences are benign-transient → roll them up ("forwarder X dropped 3% of EID1 fields this hour"), don't fire per event. This also defends the second-order attack: an adversary inducing benign-looking gaps to manufacture noise and hide the one gap that matters. Baselined benign absences make the anomalous one stand out instead of hide.
  • Correlation breaks the tie. Distinguishing benign-transient from attacker-induced is often impossible per-event — hold as NONE / escalate; let correlation decide (a lone dropped field is noise; a cluster of drops around a credential-access window on the implicated host is evidence).
The one-line statement. An absence is two claims, not one — "does it break my ∀" (security, occasional, into the verdict) and "why is it gone" (health, usual, its own benign↔problematic spectrum, its own owner) — riding separate channels that join only when correlation promotes a health-gap into security evidence.
