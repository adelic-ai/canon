Sysmon EventID 1 → OCSF: the mapping by operation type

OCSF defines the destination addresses and types. The parse is yours — and it's six different operations, not one rename.

canon · ingestion mechanics · 2026-06-12 · companion to ocsf_json_vs_rdf.html

The tempting picture is a lookup table (CommandLine → cmd_line). The real mapping is a spectrum of operations, and the pure rename is the easy minority. Here is a real Sysmon EventID 1 (process creation) → OCSF Process Activity (class_uid 1007) mapping, annotated by what each field actually requires.

The six operations hiding in "put this value at that address"

  1. Pure re-address — CommandLine → process.cmd_line. A key remap into a nested path. The bulk of fields, and the only part that's a "naming convention" lookup.
  2. Value transform — Hashes is a single compound string; OCSF wants an array of objects. You parse / destructure the value. Not a rename.
  3. Format / enum / split normalization — UtcTime string → epoch-millis int; IntegrityLevel "High" → enum id; User "CORP\svc_backup" → two fields.
  4. Constant / class assignment — class_uid=1007, activity_id=1 aren't in the record at all. You assign them because you decided "Sysmon EID1 ≡ OCSF Process Activity / Launch." This is the interpretive heart, and it's per-EventID, not per-field.
  5. Flat → nested restructuring — Sysmon is flat; OCSF distributes it across a tree (Parent* sinks under process.parent_process.*, Image+Hashes under process.file.*).
  6. Envelope vs payload merge — device.hostname comes from the Windows Event Log wrapper (System.Computer), not Sysmon's EventData. The mapper reads two levels.
Lossy both ways. Sysmon fields with no OCSF home (FileVersion, Company, OriginalFileName) get shoved into an extension or dropped; OCSF fields Sysmon never provides stay null. So the mapper is a fallible artifact — a claim with a measurable fidelity, and the natural home for a fidelity attestation ("this mapper, on this corpus, preserved these fields, dropped those, asserted EID1≡1007").

Why EventID leads — it's the type selector, not just a column

A log row, in the usual mental model, is a tuple: {timestamp, processId, process, eventID, user, …} — and eventID looks like one column among many. But it isn't. The eventID is the type tag that selects the record's whole structure — which fields are present, what they mean, and (operation 4) which OCSF class the row becomes. In coordinate terms it's a meta-coordinate: it picks the subspace, and the remaining fields locate the point within that subspace.

eventID            =  WHICH axes apply        (EID1 → Process-Activity space; EID10 → Process-Access space)
the other fields   =  the POSITION on them     (the "context" of this occurrence)

That's why monitoring leads with the eventID: it tells you which space you're in before the rest of the row means anything.

From mapping to detection: verify the context

And this is the bridge to what canon actually does. An event type is neutral. EID1 — a process started — happens constantly; the eventID alone is never malicious. What is or isn't malicious lives entirely in the context: the values of the other coordinates and the neighborhood they pin (the process, its parent, the user, the binary). rundll32 starting is fine; rundll32 starting with comsvcs.dll, MiniDump against lsass under svc_backup at 3am is not.

So detection here is not "hunt for bad events." It is, given an event of a known type, validate that its context is correct — a three-way outcome:

The eventID does double duty: it selects the subspace (which fields are the context) and it routes which context-checks apply — EID1 → process-lineage legitimacy; EID10 → the GrantedAccess mask; an auth event → the logon context. Event type + data-component → the applicable verifier set. Detection becomes per-event context-validation, dispatched by type.
