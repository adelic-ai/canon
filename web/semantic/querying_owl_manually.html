Querying OWL manually

An OWL ontology in a file is just RDF triples. There are two acts: query what's written, and query what follows.

canon · hands-on · 2026-06-10 · runnable: design/probes/d3fend/query_d3fend.py · data: packages/semantic-cyber/data/d3fend.ttl (45,139 triples)

All output below is verified against canon's real D3FEND ontology — not illustrative. The one finding that justifies doing this by hand: d3f:ServiceTicket does not exist (the notes and a test fixture both referenced it); the real class is d3f:KerberosTicket. You catch that in one query; you'd never catch it by trusting the prose.

The one thing to internalize: OWL-in-a-file is just triples

A .ttl is a pile of (subject, predicate, object) statements. There is no magic "OWL object" — the OWL axioms are themselves ordinary triples that happen to use owl: / rdfs: predicates. So "querying OWL" splits into two genuinely different acts:

  • Query IT — look at the triples that are written down (SPARQL / direct lookups).
  • Query THROUGH it — follow subClassOf / restriction paths, or run a reasoner to get triples that logically follow but aren't written.

That distinction is the whole game. Most of what you want is the second.

Querying IT — SPARQL over the asserted triples

The tool is rdflib. Load the graph, run SPARQL:

import rdflib
g = rdflib.Graph(); g.parse("packages/semantic-cyber/data/d3fend.ttl", format="turtle")

g.query('''PREFIX d3f: <http://d3fend.mitre.org/ontologies/d3fend.owl#>
           PREFIX rdfs:<http://www.w3.org/2000/01/rdf-schema#>
           SELECT ?c WHERE { ?c rdfs:subClassOf d3f:DigitalArtifact }''')
# DigitalInformation
# DigitalInformationBearer        ← only 2: the taxonomy is DEEP, not WIDE

SELECT … WHERE { triple patterns } with ?vars is the bread and butter. ASK { … } returns a boolean ("does this relation hold?"). That is the one-hop, literal reading — what's directly stated.

Querying THROUGH it — three mechanisms, in rising power

1. Property paths — transitivity without a reasoner

Append + (one-or-more) or * (zero-or-more) to a predicate and SPARQL walks the chain for you:

SELECT ?s WHERE { d3f:KerberosTicket rdfs:subClassOf+ ?s }
# -> AccessToken -> Credential -> DigitalInformationBearer
#    -> DigitalArtifact -> Artifact -> D3FENDCore

This is the subsumption reasoning the d3fend.py walker does by hand — and it's what makes the join work: a defense that monitors Credential covers a stolen KerberosTicket because KerberosTicket subClassOf+ Credential. Confirm it with ASK:

ASK { d3f:KerberosTicket rdfs:subClassOf+ d3f:Credential }   # -> True
# sanity: does d3f:ServiceTicket exist at all?            -> False

2. Walking into restrictions — the actual meat of OWL

The interesting content isn't subClassOf between named classes — it's the owl:Restriction blank nodes. "T1003.001 accesses a Process" is encoded as:

<T1003.001-class> rdfs:subClassOf [ a owl:Restriction ;
                                  owl:onProperty     d3f:accesses ;
                                  owl:someValuesFrom d3f:Process ] .

So to read "what does this technique act on," you query into the anonymous restriction node:

SELECT ?prop ?art WHERE {
  ?t  d3f:attack-id "T1003.001" .
  ?t  rdfs:subClassOf ?restr .
  ?restr a owl:Restriction ;
         owl:onProperty     ?prop ;
         owl:someValuesFrom ?art .
}
# --accesses--> Process
# --accesses--> AuthenticationService
Gotcha: the parent class T1003 carries no restrictions — they live on the sub-techniques (T1003.001 …). The d3fend.py walker handles that bidirectionally (a query on the parent picks up the children's restrictions, and vice-versa). Query a parent and get nothing, and this is why.

The other half of the join — "which defensive techniques act on Process?" — is the same walk from the defense side:

# Application-basedProcessIsolation --isolates--> Process
# HostReboot                        --terminates--> Process
# Kernel-basedProcessIsolation      --isolates--> Process   ...

3. A reasoner — entailment SPARQL can't reach

Property paths give you transitivity. A full OWL reasoner (owlready2, wrapped in semantic_core/reasoning.py) additionally infers new triples — most importantly, classifying an individual into a class by its properties ("a Process opening a VM_READ handle to lsass is-a CredentialDumpingEvent"). That is the detection-as-subsumption move. You materialize() the entailed closure, then query the enriched graph.

The performance rule you'll hit immediately

d3fend.py records that one query — a double subClassOf* with both ends unbound (all-pairs cross-join) — hung 20+ min in rdflib on the real 3.4MB ontology. The rule that falls out:

  • Seed-bound path queries (one end fixed, like every query above — d3f:KerberosTicket subClassOf+ ?s) are fast even in plain rdflib (sub-ms to ~100ms).
  • All-pairs (?a subClassOf* ?b . ?b subClassOf* ?c) blows up.
  • For repeated closure work, reason / materialize once at the schema, then per-event queries are cheap typed lookups — never run the reasoner per event.

How to actually poke at it

Three options, increasing ceremony:

  • The script: .venv/bin/python design/probes/d3fend/query_d3fend.py — edit a query, re-run. Start here.
  • A REPL: .venv/bin/python, then import rdflib, parse, and for r in g.query(q): print(r). Good for one-offs.
  • A real triplestore (Oxigraph / Jena / GraphDB) if you outgrow rdflib's SPARQL engine — they optimize the joins rdflib doesn't. Not needed yet.
The point of doing it by hand: the manual query already caught that d3f:ServiceTicket is a fiction. You find that in one ASK; you'd never find it by trusting the prose. Verify the data, tier-and-use the schema.
