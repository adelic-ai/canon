Set / Type / Category — three notions of "same rule"

The three ways canon asks "are these two rules the same?" line up with the Set / Type / Category perspectives — and the bugs live in the gaps between them.

canon · speculative · 2026-06-21 · plausible, not proven · "three perspectives," not the trichotomy theorem

Three different "same?" tests, borrowed from how mathematics gets founded three ways — and the correspondence is precise enough to explain where detection structure and detection behavior part ways.

The mapping

PerspectiveCanonNotion of "same"
Setclause_setsame set of conditions — extensional. The lattice's ⊆ / ∩ algebra is set theory → "broader / overlaps / neighborhood."
Typecontent_digestsame construction — intensional. Same conditions wired differently (OR vs AND, different filters) ⟹ different.
Categorycatch-set / behaviorsame mapping (events→fire) — observational. Known by its arrows / co-catch, not its insides.

The axes — the load-bearing part

Set and Category are orthogonal axes, not points on a line. They disagree in two independent directions — exactly ground_lattice's two off-diagonals:

  • Set-same, Behavior-different = over-grouping — the svchost pair: identical clause-set, opposite catches (same search, different filters).
  • Behavior-same, Set-different = under-grouping — the comsvcs pair: totally different clauses (CallTrace vs StartModule), same catch.
ground_lattice is literally a map of the disagreement between the Set axis and the Category axis. And Type is the meet — the finest: content_digest-same ⟹ both clause_set-same and behavior-same. It's the one corner where the axes coincide and no disagreement is possible. (Which is why swapping the grounding's Set-exact for the Type-exact was wrong — it collapsed the very axis the grounding exists to keep open.)

Is it S₃ / a symmetry? No — but there's structure

Not the symmetric group: the three aren't interchangeable. Type is distinguished (strictly finer, implies the others) and Set ∥ Category are incomparable (neither implies the other — that's the two off-diagonals). No group permutes them freely. What there is: a refinement partial order with forgetful maps (Type → Set drops construction keeping extension; Type → Category drops construction keeping behavior) — directed and information-losing, not symmetric. The one place an S₃-flavored thing lives is upstream in the foundations — Set/Type/Category as foundations inter-translate in a triangle (sets-as-types, categorical-semantics, categories-from-sets), more symmetric. Our instance breaks that symmetry by making Type the meet.

Why it's more than a cute analogy — perspective ↔ intent

It tells you which perspective fits which job:

  • Set — the lattice's relationships and neighborhoods (intersection, subsumption). The intent isn't dedup; it's the intersections — and set algebra is exactly that.
  • Type — narrowly, true duplicate detection (byte-identical logic).
  • Category / behavior — the ground truth you validate against (catch-set).
The bugs live in the gaps between the axes — over- and under-grouping are precisely where Set and Category disagree. That's not a defect of one perspective; it's why you need more than one, and why grounding (the Set↔Category comparison) is an irreducible step.
Honest caveats. An instance of the Set/Type/Category shape, not the foundations themselves; "three perspectives," not the trichotomy theorem. The legs aren't equally tight — Set↔clause_set and Category↔behavior are near-literal; Type↔content_digest is the loosest (type-theory-flavored, not literal type theory). Plausible, not proven — the value is the map of where structure and behavior part; drop the foundational dress the moment it stops paying for itself.
