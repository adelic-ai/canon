Are These Two Rules the Same?

A bottom-up derivation of why detection needs the Semantic Web.

on 3,748 real detection rules · everything reproducible from the corpus

The Semantic Web has an explanation problem. It is always pitched from the top down — a global web of machine-readable meaning — and the pitch never lands, because nobody can see what they would build. So let's not pitch it. Let's take one small, concrete question, push on it honestly, and watch the famous constructions — concept lattices, graded relations — appear not as theory but as the only answers left standing.

The question is this: are these two detection rules the same?

It sounds trivial. It is not. By the end you will have rediscovered FCA and SKOS — two acronyms from the Semantic Web stack — without ever being told to adopt them, because a pile of real rules will have forced them on you. The point of the exercise is not to sell the Semantic Web. It is to show that you re-derive its pieces the moment you take meaning seriously on real data — which is the only honest reason to want them.

A note on scope, stated up front so it can't drift: this justifies the constructions — explicit concept structure and graded relations. It does not argue for the whole W3C tower (reasoners, triple stores, the linked-data cloud). "Why you need these ideas," not "therefore adopt everything."

1What a rule is, just enough to be concrete

The corpus is Sigma — the open standard for writing detection rules. We have 3,748 of them sitting in a local copy. A rule is a small structured object: it reads fields off a log event and combines tests with boolean logic. Here is the shape, stripped to essentials:

detection:
  selection:
    Image|endswith: '\mimikatz.exe'
  condition: selection

That single test — Image|endswith: '\mimikatz.exe' — is an atom, and it has three parts:

  • field — Image, the event key being read;
  • predicate — endswith, how to compare;
  • value — \mimikatz.exe, what to compare against.

A rule is a boolean combination of atoms — atoms joined by and, or, not. And the predicate vocabulary is small. The entire set of comparisons a rule can make is roughly this:

= / globexact match, or wildcard match if the value has */?
containssubstring
startswith / endswithprefix / suffix
reregular expression
cidrIP-in-subnet
gt / gte / lt / ltenumeric comparison

Hold onto that smallness. The predicates are almost all string operations. It will turn out to be the crux of the whole essay — but we can't see why yet. First we have to try, and fail, to answer the question the easy way.

2The naive answer: are the texts equal?

The first instinct is to compare the rules as text. Two YAML files; are the bytes equal? This fails immediately, because the same detection can be written many ways:

# rule A            # rule B — same detection
  selection:           selection:
    Image|endswith:      CommandLine|contains: 'mimikatz'
      - '\mimikatz.exe'      Image|endswith: '\mimikatz.exe'
    CommandLine|contains:
      - 'mimikatz'
  condition: selection   condition: selection

Reordered keys, list-vs-inline, a stray space — byte-different, behaviorally identical. Text equality answers "different," and it is wrong. We need to compare what a rule is, not how it was typed. So we abstract away from the syntax and look at structure.

3A real idea: group rules by their fields

Here is the first genuinely principled move. Forget the text; ask which fields does this rule read? Rule A and rule B both read {Image, CommandLine}. Group rules by their field-set and you have collapsed the syntactic noise: two rules in the same group are "the same concept" — they look at the same part of the world.

This is Formal Concept Analysis (FCA), and you just re-invented it. FCA is the mathematics of exactly this move: a set of objects (rules), a set of attributes (fields), and the concepts that fall out — the closed groupings where "every rule with these fields" and "every field in these rules" line up. The groups form a lattice ordered by specificity. You didn't reach for it because a spec told you to; you reached for it because "compare the structure, not the text" is grouping by attributes, and that is FCA.

And it works — for a while. Genuine duplicates, the same detection typed twice, land in the same concept and collapse. Across the corpus this is real signal: of 3,748 rules, the distinct field-set concepts number in the hundreds, not thousands. The redundancy is enormous, and FCA is the tool that measures it.

So we have our answer to "are these two rules the same?" — they're the same iff they share a field-set concept. Clean. Principled. And, on real data, wrong.

4The wall: over-collapse

The field-set key is value-blind. It sees which fields a rule reads, never what values it looks for. Watch what that does. Consider thirty-two distinct macOS detections — thirty-two genuinely different rules, each hunting a different command, a different binary, a different argument — that all happen to read the same field, CommandLine:

32 distinct detections → 1 concept. Same field-set ({CommandLine}), thirty-two different values. The FCA key folds all thirty-two into a single concept and declares them "the same rule." They are not. One catches a credential dump; another catches a persistence trick; the key cannot tell them apart, because it threw the values away.

This is not a tuning bug. It is the structure of the move. The instant you abstract from "the text" to "the fields," you abstract past the values, and the values are most of the meaning. Grouping by attributes was the right instinct and the wrong granularity. Equality of structure over-collapses.

5A finer key — and why it still isn't enough

The fix seems obvious: stop being value-blind. Hash the rule's full compiled logic — fields, predicates, and values, the filters, the keywords, everything — into a content signature. Now the thirty-two macOS rules have thirty-two different signatures. 32 → 32. The over-collapse is gone; genuinely identical logic still collapses, genuinely different logic stays apart. Value-aware equality is the right answer to "are these byte-for-byte the same detection?"

But notice what we can now say, and what we still can't. We can say identical or not identical. That's it. Equality — however fine-grained — is a yes/no. And the real relationships between rules are not yes/no. Open the corpus and you find, everywhere:

  • one rule that is a more specific version of another (it adds a condition);
  • two rules that overlap — they catch some of the same things, and each catches things the other misses;
  • two rules that are synonyms — different fields, different predicates, but they're after the same behavior.

None of those is "the same." None is "different." They live on a spectrum, and equality — the only tool we have left — can't address a spectrum. We've run out of road on identity. We need relationships that come in degrees.

6What you're forced into: graded relations

So you invent the missing vocabulary. You need to say not just "same / different" but:

exactthese two are the same detection
closenearly the same — interchangeable for most purposes
broaderthis one is a more general version of that one
narrowerthis one is a special case of that one

That is SKOS — the Simple Knowledge Organization System, the Semantic Web's vocabulary for exactly these graded relations (exactMatch, closeMatch, broadMatch, narrowMatch). And, again — you did not adopt it. You were forced into it, because "same-or-not" could not express "this rule is a stricter version of that one," and your data is full of stricter-versions-of. The moment you take the relationships between rules seriously, equality is not enough and a graded relation is the minimum that works. SKOS is the name for the minimum.

This is the payoff of part one. The first place the Semantic Web stops being abstract is right here: you needed concept structure (FCA) to get past the text, and you needed graded relations (SKOS) to get past equality. Neither was a vision you bought into. Each was the next forced move when the previous tool hit a wall on real rules.

7The seam: structure is not behavior

And now the honest crack, the one that opens part two. Everything we've built — concept lattices, content signatures, graded relations — describes what a rule says. None of it knows what a rule does. And on real rules, those come apart.

Here is a single real rule that contains the whole problem. It lives at proc_creation_win_susp_parent_execute_itself.yml in the corpus, and it uses Sigma's most common idiom — a positive selection wrapped in layered allowlists:

detection:
  selection:
    Image|fieldref: ParentImage          # a process whose image == its parent's
  filter_main_path:
    Image|startswith:
      - 'C:\Program Files\'
      - 'C:\Program Files (x86)\'
  filter_main_original_fn:
    OriginalFileName: ['Cmd.Exe', 'PowerShell.EXE', ...]
  filter_main_product:
    Product: ['Microsoft Office', 'Firefox', ...]
  condition: selection and not 1 of filter_*

The selection — the part our structural key sees — is one line. The three filter_* blocks — the part the key barely registers — carry almost all of the behavior: they suppress every binary under Program Files, every known-good executable by its embedded metadata, every listed vendor's product. Take two rules with the same selection and different allowlists. To structure they are identical. In behavior they are wildly different — one stays silent on Firefox, the other screams at it. The thing that determines what the rule does is exactly the thing structure under-weights.

It gets worse, and the small predicate vocabulary from section 1 is why. With only a handful of string operations, the same catch can be spelled many ways: Image|endswith: '\mimikatz.exe' and CommandLine|contains: 'mimikatz' are different atoms — different fields, different predicates, different values, so different by every structural key we built — yet they fire on the same events. Different structure, same behavior. And the reverse, as we just saw with the allowlists: same structure, different behavior. Structure and behavior are not a fine and coarse version of one axis. They are orthogonal.

There is no structural key — not field-sets, not content signatures, not SKOS grades — that can tell you what a rule catches. To know what a rule catches, there is exactly one move left: run it. And running it needs a detector, real events, and a notion of "fired on the same instances." That is a different machine, and a different question, and it is where part two begins.

8So — why do we need the Semantic Web?

Because if you take one ordinary question — are these two things the same? — and you refuse to lie about the answer on real data, you are marched, step by forced step, through its constructions. Text equality fails, so you group by structure, which is FCA. Structure over-collapses, so you add values, which gets you to exact identity. Identity is yes/no and the world is graded, so you reach for degree, which is SKOS. None of it was abstract. Each piece was the cheapest tool that survived contact with 3,748 real rules.

That is the honest case for the Semantic Web, and it is the only one worth making: you do not adopt it as a vision. You rediscover its pieces, because the problem of meaning — what is the same, what is related, what is true — forces them on anyone who works at the level of data and won't fake the answers.

And we have stopped one question short. We learned what a rule says, and proved it isn't what a rule does. The catch — what these rules actually fire on, and the four-valued logic you need to combine many of them honestly — is the behavioral axis, and it needs a detector. Part two runs the rules.
