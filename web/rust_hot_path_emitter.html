Rust hot-path emitter — scope

…and the more general endpoint: emit standards, not emitters.

canon · scope · 2026-06-18 · the 3rd emitter for the firing path — and what it dissolves into

The motif graph already emits to Python (interpreter) and SPARQL (oracle). This scopes the third emitter — Rust, for the production firing path — licensed by the same agreement attestation. But the question worth answering first is what's the most future-proof general way, and the answer reframes the Rust emitter as a disposable stepping stone toward a standard waist.

The general principle, stated up front. A per-language emitter (Python, SPARQL, Rust, Go…) is O(targets) of hand-written backends, each re-opening the semantic-equivalence problem. The future-proof move is the discipline canon already uses for ontologies — don't re-mint, adopt the standard waist (import prov: directly; OCSF as the shared schema). Applied to execution: emit a portable plan over portable data, run by a vectorized engine. Rust stops being an interpreter you write and becomes the engine you didn't (DataFusion = Arrow + Rust).

What Rust actually buys — honestly

The hot path is "fire thousands of rules over billions of events." The Python emitter is fine for one rule over a corpus — str.endswith is C-speed in CPython — so the per-predicate speedup is not the win, and overselling it would be wrong. What a native path buys is three things the Python path structurally can't:

LeverWhy Python can't
the dispatch loopthousands of rules × N events is a pure-Python nested loop; the interpreter overhead, not the comparison, dominates.
parallelismevents are independent — embarrassingly parallel — but the GIL makes data-parallelism awkward. rayon over cores is free.
deployment shapea standalone worker over a stream/shard is the at-scale deployment; the same artifact serves production and the attestation harness.

The two forks — with recommendations

DecisionOptionsRecommendation
emission strategy interpreter-in-Rust (read the motif graph as data) vs codegen (generate + compile Rust per rule). Interpreter first. Captures the loop + parallelism + deployment wins with no runtime rustc. Codegen is a layer-2 optimization, built only if profiling says dispatch bounds throughput.
the boundary subprocess/streaming (JSON in/out) vs PyO3 (in-process extension). Subprocess. It is the deployment model and serves the gate (pipe a corpus, diff firings); Python tests skip it when the binary's absent. PyO3 is a later convenience.

The semantics profile — the hard part, and the whole point

Structure ports; semantics don't. Rust vs Python diverge on enumerable landmines, and surfacing them is the value — today the IR's string semantics are implicit (the Python emitter just uses its defaults). The slice must pin a semantics profile in the IR so every emitter targets the spec, not its language:

LandminePin
case-foldingPython .lower() vs Rust to_lowercase() agree on ASCII, differ off it (final sigma, ß). Pin ASCII-case-insensitive — a one-line correction to sigma_eval may be the first artifact.
substring / endswithcode-points vs UTF-8 byte boundaries — agree for valid UTF-8 (JSON guarantees it). Pin it.
missing fieldboth default to "". Pin it.
non-string coerciona real divergence: str(True)="True" vs serde true; number formatting differs. Pin a canonical coercion or the attestation flags bools/numbers.
wildcardsneither globs * (literal) — consistent, but pin so a future emitter doesn't "helpfully" add it.

The gate — extend agreement to N emitters

attest_emitter_agreement already compares Python ↔ SPARQL; extend to Python (oracle) ↔ SPARQL ↔ Rust, pairwise, each disagreement localized to (emitter, event, rule). Two additions: Rust runs as a subprocess in the harness (batch, no PyO3); and the corpus must include the landmines above.

OTRF is the happy path — it won't exercise non-ASCII, bools, numeric fields, empty strings. The gate needs an adversarial edge-case corpus, and that is exactly where the dataset-generator earns its keep: generate, by construction, the events that stress the semantic seam. A green N-emitter attestation is the license to run the fast path in production; a red one is a finding — it names the semantic the IR hadn't pinned.

The more general endpoint — emit standards, not emitters

Where this all wants to go. Instead of hand-writing backends, emit a portable plan over portable data, run by a vectorized engine:

ruleset  ──compile──▶  Substrait plan   (the open, cross-engine query-plan standard — ONE emitter)
events   ──────────▶  Arrow columns    (columnar batches — the SIMD / cache lever)
                       │
                       ▼
              vectorized engine          DataFusion (Arrow+Rust) embedded · DuckDB · Velox · Spark
                                         → "the Rust emitter" DISSOLVES: Rust is the engine you didn't write

Why it's better at scale, not just trendier:

  • Vectorized/columnar is the real hardware lever for billions of events; a row-at-a-time interpreter (Python or bespoke Rust) leaves SIMD + cache locality on the table.
  • You inherit the optimizer — common-subexpression elimination shares a predicate a thousand rules all check (TargetImage endswith \lsass.exe computed once), reordering by selectivity, indexing — none hand-written.
  • Hot and cold unify — the same plan-IR expresses "fire rules over events" (hot) and "which rules cover T1003.001" (cold, a query over the rule table). One engine, two plans.
  • Portability for free — one plan runs embedded, distributed, or in a warehouse; a new target is a new Substrait consumer, maintained by someone else.
Honest limits — this over-reaches if unbounded. Field-match/suppression molecules are perfectly relational (conjunctive predicates) — most of the Sigma hot path maps cleanly. But correlation/multi-EID molecules are windowed self-joins (more friction + state), and the statistical battery (MI, CFAR, circular stats) is not relational at all — custom aggregations that attach as UDF/UDAF, not SQL. So the general form is layered: a portable plan for the relational majority + a UDF escape hatch for the non-relational primitives. And the semantics-pinning problem recurs as "the engine's ends_with vs the spec" — the profile and the attestation remain the license, unchanged.
So the Rust interpreter is a disposable stepping stone — named as such. The semantics profile is the hard part and is cheaper to pin in a ~200-line Rust interpreter than inside a query engine. Keep the interpreter only to nail the spec; treat it as throwaway; make the named production endpoint "emit Substrait/Arrow to a vectorized engine," not the bespoke interpreter. Cheap rung to learn the semantics; standard waist for the real thing — earned-not-designed, one level up.

One line. Your instinct toward Rust is right — but the general form isn't "hand-write a Rust interpreter," it's "emit a portable plan that a Rust/Arrow engine runs." Don't build backends; emit standards.
