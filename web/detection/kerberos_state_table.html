Kerberos as the entailment demo

The state-table KDC, SPIFFE by contrast, and where canon stays general.

canon · thinking capture · 2026-07-25 · identity is latent · anchor on crown jewels · Kerberos is a state machine · forgeries are GAPs · KDC+ vs canon

Kerberos is where the entailment thesis stops being a stretch and becomes obviously correct: the protocol is a state machine with hard necessity relations, so the "absence of a necessary step becomes evidence" mechanism (the GAP) shows at its cleanest — a forged ticket is a used-without- issued gap in the state machine. This page captures the arc: why identity is latent, why we anchor on crown jewels, why Kerberos is the ideal domain, the state-table KDC POC, and why KDC+ is the answer where you own the protocol while canon is the answer where you don't.

Setup: identity is latent, so anchor on the crown jewels

Generic attacker-identity resolution is close to hopeless against a competent adversary. The surface "who" (the W-record's account/principal) is observed; the actor is a latent variable wearing many identities. Shared-observable joins (same client IP, etc.) catch the lazy roaster and evaporate against anyone who rotates infra — IP is a floor, not an answer.

The tractable reframe: don't resolve identity from scratch — anchor on the standing-suspect, crown-jewel-adjacent principals (service / admin accounts, always the target) and watch for partial chains assembling around them (online, on the prefix, before the pivot). Identity becomes a weak label on a hypothesized chain, not a resolved fact. And the chain canon reconstructs is a hypothesis consistent with the observations — never the path the attacker actually took. The watch-set is the org's own privileged surface (the allowlist read as the watch-set).

Can SPIFFE help? — prevention, not detection

Yes, but by removing the attack surface, not by improving detection, and only for one slice. A SPIFFE service has no password-derived long-term key, so there is nothing to kerberoast and no keytab to steal — its identities are short-lived, attested, per-workload. Two gains:

  • Removes the standing-secret class for workload-to-workload auth (most of what gets kerberoasted).
  • Cleans up the "who" — every action ties to an attested SVID instead of a shared service account, so the identity-linkage problem gets easier in a SPIFFE estate. (See the full stack: agent identity in the enterprise.)

But this is the world you'd build fresh, not the one you're defending. It doesn't help you detect on the deployed AD estate.

Could Kerberos be replaced by SPIFFE? — partially, and not where it matters to you

DomainSPIFFE replaces Kerberos?
Cloud-native service-to-serviceYes — arguably better (no standing secrets, attestation-based); orgs are already moving this off Kerberos to mTLS/SVIDs.
AD / Windows estateNo — interactive human SSO, SMB, RDP, LDAP binds, the realm backbone. Decades of integration in LSASS/SSPI/GSSAPI. SPIFFE isn't even designed for interactive human logon.

So they coexist for the foreseeable future — and that is exactly why Kerberos detection stays canon's job: the vulnerable protocol is the deployed one. SPIFFE's real use here is as the contrast that explains the attack class: kerberoasting, silver and golden tickets all trace to two design facts — standing password-derived keys and forgeable long-lived tickets under a single krbtgt key. SPIFFE has neither.

Kerberos is the ideal domain for entailment — the necessity is a protocol invariant

The protocol is a state machine, and its necessity relations are Mendelian (hard rules), not statistical:

AS-REQ  → AS-REP   (TGT, encrypted under the krbtgt key)          [EID 4768]
TGS-REQ → TGS-REP  (service ticket, under the SERVICE account key) [EID 4769]
AP-REQ             (present the service ticket to the service)     [EID 4624 network logon]

necessity:  a valid AP-REQ to service S  ⊢  a prior TGS-REP for S  ⊢  a prior AS-REP (TGT)

And the forgery attacks manifest as GAPs in that state machine — the exact CONFIRMED / GAP / NONE mechanism (absence made legible), now protocol-grounded:

AttackState-machine signaturecanon reading
Golden ticketforged TGT (krbtgt key) — used normally, so it does emit 4769s; the tell is the v2 ticket-hash correspondence: a presented TGT hash (4769.RequestTicketHash) that no issuance (4768.ResponseTicket) ever producedpresented-without-issued → GAP → krbtgt compromise. Kerberos splits cleanly along the thesis line: roasting/fan-out is statistical (the battery), and the TGT forgeries are entailment GAPs (a presented ticket with no issuance). The forged ticket is the strongest possible demonstration of "a necessary-but-missing step is evidence" — the necessity is a protocol invariant, not a domain heuristic. canon already has the worked SIEM detector — ticket-integrity (Splunk, KV-Store ledger) / (Sentinel, KQL) — reconstructing the issued-ticket registry from the v2 hash correspondence (4768.ResponseTicket ⇄ 4769.RequestTicketHash) and firing on presented-without-issued. Scope: that is TGT-integrity (golden, pass-the-ticket), all DC-side; silver tickets skip the KDC and need member-side fusion — the frontier in the table above. Plus validated roasting detections (fan-out cross-check, the honest T1558.003 real-data bound, the kerberoasting tangent). What today's page adds is the state-model framing and the GAP vocabulary over that existing detector.

The POC: rebuild Kerberos with the state table built in

MIT krb5 is permissively open source, so forking or instrumenting it is fair game. "Attach a state table to the kernel" — meaning the KDC core, not the OS kernel — has two paths:

  • Instrument MIT krb5 — hook the KDC issuance path via its audit-plugin interface (an existing extension point) to emit the state transitions. Real-protocol fidelity, but you're in heavy C.
  • Write a minimal KDC with the state table native (AS / TGS / AP + ticket lifecycle + key derivation only). Faster, fully controllable, and you use real MIT krb5 as the ground-truth oracle to check your minimal one behaves.
v0 = the minimal KDC. It solves three problems this whole thread raised, at once:
  1. The testing problem — a Kerberos you control is a ground-truth generator: emit labeled benign + attack telemetry, inject a silver/golden/PtT ticket, and you know exactly which invariant it violates. Better than hand-authored fixtures because the labels come from the implementation.
  2. The entailment rules stop being guessed — with the state table explicit, the necessity relations (AP-REQ ⊢ TGS-REP ⊢ AS-REP) are derived from the protocol. "Understand it like we made it" becomes literal.
  3. The GAP thesis gets its cleanest demo — a forged ticket lighting up because its entailed issuance event is missing, on a domain the Black Hat room respects (Kerberos downgrade/DoS/takeover is on the 2026 program).

Scope it hard. The value is the state machine + ticket lifecycle + key derivation + two or three injectable attacks — not RFC 4120 compliance. Don't build production Kerberos.

Keep two things staged, don't conflate them. The minimal-KDC POC above is a test-stand and rule-source (near-term, buildable). Separately, "KDC+" — a Kerberos redesigned so tickets carry their own issuance provenance (a self-validating auth protocol, canon's "carry your proof" applied to the protocol itself) — is a much bigger swing, and it hits the same adoption wall as SPIFFE. Same codebase to start; very different timelines to land.

KDC+ vs canon — prevention plane vs detection plane

The relationship is not on-ramp → answer. It is the same symmetry as SPIFFE-vs-Kerberos:

 KDC+ (state table built in)canon
Planeprevention / proof at the sourcedetection from the outside
Analogythe Kerberos version of SPIFFE — "build it right"detect on what's actually deployed
Works whereyou can deploy it — greenfield / long migrationthe un-modifiable AD estate that's everywhere
Exposes forgery byconstruction (state is intrinsic)inference (the entailed issuance event is missing → GAP)
One line: KDC+ proves forgery can't hide when you own the protocol; canon proves you can still catch it when you don't. Both are needed because migration never finishes.

Why canon stays general (don't let KDC+ demote it)

KDC+ fixes one protocol; canon is the general entailment-over-telemetry substrate. Kerberos isn't canon's scope — it's canon's sharpest demo, because the necessity relation is a hard protocol invariant so the GAP shows at its cleanest. Prove the thesis on Kerberos, then point out the same machinery eats CloudTrail, process trees, and the comsvcs ⊢ lsass-read case (the entailment engine, over the knowledge stack) — domains where no "KDC+" exists and external detection is the only option. This mirrors the two halves of the broader agent-security picture: detection/warrant (canon) feeding the policy/enforcement plane (agent detection / agent identity) — the same monotone-fold-over-a-DAG on both ends.

One line

Kerberos is the domain where entailment is obviously right (the necessity is a protocol invariant; forgeries are GAPs). Build the minimal state-table KDC as the ground-truth generator and rule-source; let KDC+ be the greenfield "build it right" bet it seeds; and keep canon as the general detector for the deployed reality no protocol fix will reach.
