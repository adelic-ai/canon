Kill-chains as entity-path analysis

Detecting a kill-chain is the same shape of problem as e-business navigation/funnel analysis — sessionize per actor, see which segments of the path-to-crown-jewel assembled, score by completeness and abnormality.

canon · design note · 2026-06-21 · the frame behind detection/chain.py

Detections don't go away — they become the observables

The kill-chain view doesn't replace detections; it composes them. The stages are detections (a 4768 auth, an RC4 TGS fan-out, a logon to a crown jewel). What changes is the unit and the question: from "did this detection fire?" to "is a path toward a crown jewel assembling?"

The factoring shifts with it: earlier, atoms factor rules (a shared clause is one atom); now, segments factor paths — the kill-chain graph has shared edges (many attacks traverse the same lateral-movement segment), so paths decompose into reusable segments the way rules decompose into atoms. Same move, one level up.

The scoring — completeness × abnormality

The boolean chain checker answers a corner: is the full path present, in order? The fuller, abductive question has two factors:

  • Completeness — how much of a coherent path toward a crown jewel is assembled (1 stage vs 3 in order).
  • Abnormality — weighted by how abnormal that path is for this account. A service account fanning out to SPNs may be half-normal; a finance user doing it is not.
threat-likelihood ≈ completeness × abnormality. The boolean chain is the completeness = full, abnormality = ignored corner; the abductive layer generalizes both — more of the path + more abnormal for this entity → more likely a real actor.

Where the analogy honestly breaks

  • Adversarial — web users follow cooperative funnels; the attacker hides the path, varies tools (LOLBins), improvises. No designed funnel; the negative class is overwhelmingly benign.
  • Sparse positives — millions of conversions vs a handful of real attack paths; the tiny-positive-class problem dominates.
  • Abnormality is data-gated — "normal for this account" needs the account's history (or its segment's baseline), standing longitudinal data. The recurring data-shape wall: completeness (the boolean chain) is checkable on one capture and built; abnormality needs the baseline data we keep running short of.
Takeaway. Detections are the observables, the path is the unit, the frame is e-business-style entity-path analysis. The boolean completeness layer is buildable now (the chain checker); the abnormality weighting is the next layer — and it is the part that waits on longitudinal baseline data.
