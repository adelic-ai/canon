Kerberos Ticket-Integrity Detection — Splunk

Golden Ticket & Pass-the-Ticket via issued-vs-presented TGT hash correspondence.

design draft · reconstruct the issued-ticket registry the KDC does not keep · SPL is a starting point to validate — field names/extractions must be confirmed locally

Events 4768 (TGT issued) and 4769 (service ticket requested), in their version 2 form (Windows Server 2016+ with the 2025-01-14 cumulative update or later), log the hash of the ticket. That lets the log layer rebuild the issuance ledger the KDC deliberately does not keep, and enforce one invariant: every TGT presented in a 4769 must correspond to a TGT actually issued in a 4768.

  • Presented TGT hash that no 4768 ever issued → forged TGT (Golden Ticket).
  • Legitimately issued TGT presented from a different client context than issuance → stolen ticket reuse (Pass-the-Ticket).
In Splunk this maps cleanly because the KV Store lookup is mutable: the live table of currently-valid issued TGTs is a KV Store collection you upsert, read, and reap — the true live-table semantics an append-only store (see the Sentinel version) can only approximate.

1. Why it works — and the one hard assumption

Kerberos validates a presented ticket cryptographically (it decrypts under the krbtgt key and its signatures hold), not by looking it up in a registry of issued tickets. The KDC keeps no such registry — by design, for statelessness and multi-DC scale. That is exactly why a Golden Ticket works: an attacker holding the krbtgt hash forges a TGT that decrypts and validates perfectly, and the KDC has no issuance memory to contradict it.

The v2 hash fields let a centralized log platform rebuild that missing registry — stateful, bounded (only currently-valid tickets, ~10h up to ~7-day renewable), and off the request hot path: the three things the KDC could not be.

Hard assumption: the check is only as sound as 4768 collection completeness. A legitimately issued TGT whose 4768 was not collected will look forged. Issuance-log coverage is a first-class prerequisite (§7).

2. Prerequisites

  1. Patch/OS level. DCs on Windows Server 2016+ with the 2025-01-14 CU or later, emitting 4768/4769 v2. Unpatched DCs do not emit the hash fields — the detection is blind on them (fail-open; inventory them).
  2. Auditing. Audit Kerberos Authentication Service (4768) and Audit Kerberos Service Ticket Operations (4769) enabled on all DCs.
  3. Ingestion — verify first. The hash fields are new, so Splunk_TA_windows likely has no extraction for them yet. Confirm they arrive in the raw event: 
    index=<win_sec> (EventCode=4768 OR EventCode=4769) | head 20 | table _raw
    Look for RequestTicketHash, ResponseTicketHash, ResponseTicket. If absent, fix collection before writing any detection (forwarder inputs / WinEventLog rendering / DCR).

Field-name reference (asymmetric — key detail)

EventMeaningTicket-hash field(s) in EventData
4768TGT issued by DCResponseTicket (the issued TGT)
4769Service ticket requested (client presents its TGT) RequestTicketHash (TGT presented) · ResponseTicketHash (service ticket issued)
The correspondence to key on: 4768.ResponseTicket ⇄ 4769.RequestTicketHash. Confirmed against Microsoft's own sample events, which show the same base64 value across a 4768→4769 pair for one session.

3. Architecture

  4768 / 4770  ──ingest──▶  ┌───────────────────────────┐
  (issued / renewed)        │  KV Store:  live_tgt       │
                            │  _key = tgt_hash           │
                            │  → account, dc, issuer_ip, │
                            │    issue_time, renew_of     │
  4769 ──check(lookup)────▶ └───────────┬───────────────┘
  (presented)                           │ reaper (scheduled)
        │                               ▼  delete rows past TGT lifetime
        ├─ hit               → legitimate (enriched with origin)
        ├─ hit, ctx diverges → PASS-THE-TICKET candidate
        └─ miss              → GOLDEN-TICKET candidate

One mutable KV Store collection, three scheduled searches. Collection live_tgt: _key=tgt_hash; fields account, issuing_dc, issuer_ip, issue_time, renew_of.

4. Implementation (SPL)

Field names (TargetUserName, Service_Name, Ip_Address, host) follow common Add-on conventions but vary by TA version / CIM — verify locally. The rex assumes the hash renders as Field">value< in _raw; adjust to the real event.

4.1 Ingest — maintain the table (every 1–5 min)

index=<win_sec> (EventCode=4768 OR EventCode=4770)
| rex field=_raw "ResponseTicket\">(?<tgt_hash>[^<]+)"
| where isnotempty(tgt_hash)
| eval _key=tgt_hash, account=TargetUserName, issuing_dc=host,
       issuer_ip=Ip_Address, issue_time=_time,
       renew_of=if(EventCode=4770,"renewal",null())
| table _key tgt_hash account issuing_dc issuer_ip issue_time renew_of
| outputlookup live_tgt append=true key_field=_key

append=true + key_field=_key gives upsert. Including 4770 handles renewals (Defeater 1).

4.2 Check — the detection (every 1–5 min)

index=<win_sec> EventCode=4769
| rex field=_raw "RequestTicketHash\">(?<tgt_hash>[^<]+)"
| where isnotempty(tgt_hash)
``` referral / cross-realm cut (Defeater 2) ```
| where NOT (like(Service_Name,"%$") OR like(Service_Name,"krbtgt/%"))
| dedup tgt_hash, TargetUserName          ``` distinct TGT per user, not per access ```
| lookup live_tgt tgt_hash OUTPUT account AS issued_account, issuing_dc, issuer_ip, issue_time
| eval verdict=case(
        isnull(issued_account),  "golden_ticket_candidate",
        Ip_Address!=issuer_ip,   "pass_the_ticket_candidate",
        true(),                  "legit")
| where verdict!="legit"
| table _time verdict TargetUserName Service_Name tgt_hash Ip_Address issuer_ip issuing_dc issue_time host

4.3 Reaper — expire the table (hourly)

| inputlookup live_tgt
| where issue_time < relative_time(now(),"-7d")   ``` max renewable lifetime; tune to policy ```
``` then delete: re-outputlookup surviving rows only, or KV Store REST delete keyed on _key ```

KV Store has no reliable per-row TTL; a scheduled reaper is the robust pattern. Confirm your version's supported deletion path.

5. Defeaters & tuning

A miss is only "Golden" after these clear — they are the false-positive sources, handled as maintenance rules rather than suppressed blindly.

#Legitimate causeHandling
1Renewal — 4770 mints a new TGT hashIngest 4770 (§4.1). Without it, renewals read as Golden.
2Cross-realm — TGT issued by another realm's KDC, no local 4768Filter referral requests (krbtgt/OTHERREALM, machine $); for real coverage, federate live_tgt across realms.
3Out-of-order / late logs — 4769 indexed before its 4768Quarantine Golden verdicts briefly (re-lookup after 5–10 min); the persistent table reconciles late issuances.
4Coverage gap — DC's 4768s not collected but 4769s areNot tunable in-search — an ingestion problem. Monitor per-DC 4768 volume (§7).
5Pre-window — TGT issued before the table existedWarm-up: seed live_tgt from a ≥7-day backfill before enabling alerting.

RC4 encryption downgrade (Ticket_Encryption_Type=0x17) is a useful corroborator on a Golden candidate, not a primary signal here.

6. Alert output & triage

  • Golden candidate — presented tgt_hash, account, service, presenting IP, serving DC. The absence of an issuance origin is the finding. High severity (implies krbtgt compromise / domain persistence).
  • Pass-the-ticket candidate — presented tgt_hash with its issuance origin (account, issuer IP, DC, time) and the diverging presenting IP. The mismatch is the finding. High severity.

Triage: is the account/host expected? Does the presenting IP match the user's normal workstation? For Golden, first rule out a coverage false positive — confirm the serving DC is v2 and that account's DC 4768 coverage is healthy — before escalating.

7. Validation, testing, coverage

  • Plumbing: confirm hash fields present and extractions return values on live data before trusting any verdict.
  • Coverage health (standing): per-DC 4768 volume; alert if a DC stops emitting 4768s while still emitting 4769s — that manufactures false Golden positives. 
    index=<win_sec> (EventCode=4768 OR EventCode=4769)
| timechart span=1h count by host   ``` watch for 4768 → 0 on any DC ```
  • Positive test (lab only): forge a Golden Ticket in an isolated lab and confirm the presented TGT produces a miss; replay a real TGT from another host and confirm the context-divergence path fires. Never test against production Kerberos.
  • Negative test: confirm normal renewals, delegation, and cross-realm do not alert after the defeaters are in place.

8. Assumptions & limitations

  1. Detection, not prevention. By the time a Golden Ticket exists, krbtgt is compromised and the domain is owned. Response = krbtgt double-reset + IR.
  2. Coverage-bound soundness. Incomplete 4768 collection ⇒ false Golden positives. Coverage monitoring is not optional.
  3. Version-gated & fail-open. DCs without v2 events are invisible. Inventory patch level; treat unpatched DCs as blind spots.
  4. Cross-realm needs federation. Single-deployment, the referral cut avoids false positives but does not truly validate cross-realm tickets — only excuses them.
  5. Advanced evasion. An attacker with krbtgt who also suppresses/forges DC logging defeats a log-based control. Raises the bar; not unbeatable.
  6. The SPL here is a starting point — field names, extractions, and KV Store deletion must be validated and adapted before production use.
