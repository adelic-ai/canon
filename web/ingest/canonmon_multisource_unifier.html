canonmon — the multi-source provenance unifier

Every log is Entity/Activity/Agent. Unify them, and correlation is structural.

canon · design / vision · 2026-06-05 · extends process_provenance_graph.html

DESIGN — not yet built (the process-graph slice IS built; the multi-source unification is designed)

Sysmon is not the only log. Host process events, network flows, cloud audit, and authentication are all Entity / Activity / Agent — so they un-flatten into one content-addressed provenance graph in one vocabulary. The payoff: when the same entity appears in several sources it is the same content-addressed node, so cross-layer correlation is structural — a graph walk — not a fuzzy join.

Lateral movement = a path in the unified graph. Trace an attacker across machines, across AD domains, across operating systems, and from on-prem into cloud — because the joins are shared nodes, not correlation guesses: 
process dump (host A)  →  the stolen account is one Agent node
   account authenticates to host B   (auth log)     ── same Agent CID
      pass-the-ticket: the SAME ticket-Entity used on A and B   ── same Entity CID
         host B connects outward      (network log)  ── same host node
            IAM principal calls S3    (cloud log)    ── same identity, bridged
=  one walk through one graph; the blast-radius frontier falls out
Pass-the-ticket is the clean case: the same Kerberos ticket reused on two hosts is the same Entity node (one CID), so the reuse is visible structurally rather than inferred.

SKOS between logs — the un-flatten step is a vocabulary bridge

Each source names the same concept differently: Windows SubjectUserName / LogonId; CloudTrail userIdentity.arn / principalId; Linux uid / auid; Okta actor.id. These are the same kind of thing (a principal) under disjoint vocabularies. A SKOS layer (skos:exactMatch / closeMatch) bridges each source's field vocabulary to one identity / action / resource model — so "un-flatten into one vocabulary" is a SKOS bridge per source. Canon's semantic-core already builds SKOS bridges; the highest-value, most-divergent bridge is traditional IT ↔ cloud (on-prem AD and cloud IAM are conceptually the same — principal, credential, resource, action — but vocabulary-disjoint). The industry's OCSF effort is the same normalization aim; canon's version carries provenance + honest-NONE, not just a flat schema.

A consequence worth chasing: auth fidelity. Unify authentication across IT and cloud and the actual auth topology becomes visible — versus the intended one. The gap is the finding: controls that never constrain anything (ceremony), redundant checks, and transitively-exploitable trust relationships. This is the per-rule fidelity attestation idea applied to security controls rather than detections — "does this auth construction actually constrain anything, or is it theatre?"

The substrate is an open family of validation folds

The substrate is not one validator — it is however many independent validation lenses make sense, each a fold over the same content-addressed object. Three distinct axes, easy to conflate:

  • Folds = concerns (parallel). value · provenance · custody · validity · guarantee · confidence · temporal — independent lenses, each answering a different question. Open and extensible: add concern N without touching concern M.
  • Tiers = rigor (stacked). well-formed → bounded → machine-checked, within the guarantee fold.
  • Data-components = where (the layer axis). host / network / cloud / auth — which sensor saw it.

The membership test that keeps "however many make sense" honest: a candidate concern is admitted iff it can be written as a ≤_k-monotone fold over the DAG into the Belnap carrier (CI-checkable). If it can't be written monotone, it's rejected and re-cut. That is the governing structural idea, restated: every cross-cutting concern is a monotone fold from one content-addressed graph.

Honest scope. The single-source process graph is built; the multi-source unification, the SKOS bridges, and the auth-fidelity finding are designed, not built. Two real limits carry over: scale (millions of events/host/day — localize around flagged subgraphs, never materialize the whole graph) and log-custody (the chain still needs signing at the sensor; binary-integrity is live from hashes, log-custody is not). The auth-weakness idea is a lead, not a result — you see what is logged, not the full control logic.
