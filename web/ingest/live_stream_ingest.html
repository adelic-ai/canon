Live stream ingest — reading a forgetful source

The source remembers nothing. Continuous capture is the only history — and "detect live" is two different jobs.

canon · design · 2026-06-19 · eslogger · per-event verifier vs windowed surfacer · the daemon

macOS Endpoint Security — the kernel event API eslogger taps — is a real-time subscription that retains nothing. Each event is handed to subscribed clients the instant it happens, then dropped. There is no buffer, no ring, no look-back. So the question is never "how long does the source keep data" (zero) but "what do we capture, and what does live detection even mean over a stream." The answer splits cleanly — and the split is the same verifier/surfacer line that runs through all of canon.

1 · The source forgets — capture is the only history

Kill the reader and the stream stops cold. Events before the subscription, or during any window when no client was subscribed, were never delivered and are unrecoverable. (osquery's es_process_events is the same live model; Unified Logging persists but is thinner — no full command lines; OpenBSM persists only if configured.) You keep exactly what you capture.

A gap is a NONE, not a FALSE. Any window when the monitor was down is honest missing telemetry, never "nothing happened." That is precisely the feed-liveness signal the temporal fold already wants: a live, unbroken feed is intact chain-of-custody. canon even models it today — ingest.attest(…, feed_live=True) exists; a real stream supplies the signal instead of hardcoding it.

2 · Raw ingest is trivial — "detect live" is two shapes

Reading the stream is easy: eslogger exec emits NDJSON (one event per line); read line-by-line, normalize each through the eslogger→OCSF adapter, feed it onward. What is not one thing is "detect live" — it splits exactly along the verifier/surfacer axis:

PathShapeWhy
Sigma round
verifier		 per-event, streamable Each rule is a predicate on one event. As each event arrives: normalize → evaluate the selected rules → emit a verdict on a hit. No window, no accumulated state. Works on a single event.
Battery
surfacer		 windowed micro-batch A rarity-against-population statistic — one event has no rarity. Runs over a sliding trailing window, recomputed each interval. "Live" = re-run over the trailing window, not score each event. Not a limitation — it is what a statistical surfacer is.

3 · The reader loop

eslogger exec ──(root)──▶  NDJSON  ──(unprivileged reader)──▶  normalize (eslogger→OCSF)
                                                                │
                                        ┌───────────────────────┴───────────────────────┐
                                per-event: fire the Sigma round        every interval: run the battery
                                → verdict on a hit (streamable)        over the trailing window (micro-batch)
                                                                │
                                                       emit verdicts → workspace store

The body is a generator that follows the source like tail -f — iter_ndjson(path) yielding parsed events as lines arrive — feeding the two consumers. The per-event consumer is stateless; the windowed consumer holds the trailing window, the only in-memory state.

4 · Continuous = a daemon: one stateful engine process, bound to a workspace

"Run it continuously" means a long-running process, not the batch CLI we run today (invoke → load list → fire → exit). It is:

  • the same engine code — you don't fork or re-checkout canon; you host the library in a persistent process whose loop is the reader above;
  • detached from any interactive session — it must outlive the shell that started it, so it runs under a process manager;
  • stateful — the trailing window and the feed-liveness signal live in the process; batch runs reconstruct everything each time, a daemon accumulates;
  • bound to a workspace — the per-host state (baselines, verdict store, vocab/adapter pins, retention horizons) is workspace, not engine. One engine process pointed at one workspace = one instance. N hosts → N instances → N workspaces, one engine. For a single Mac, a single daemon.
On macOS: launchd, with a privilege split that is also good hygiene. A root LaunchDaemon runs eslogger exec and writes the stream (collection; needs root + Full Disk Access). An unprivileged LaunchAgent runs the canon reader, tailing it (analysis; never root). Two managed services, one pipe (a file or FIFO) between them — the analysis process never holds root.

5 · How we wire it — the transport (the concrete "how")

The topology leaves one load-bearing decision: what carries bytes from the root producer to the unprivileged reader. Three options, judged against canon's own rule — a gap must be an honest NONE, never silently-lost data:

TransportRestart behaviorVerdict
FIFO
named pipe		 silent gap — writes drop when no reader is attached; no replay; small buffer stalls eslogger under backpressure Zero disk, but loses data across restart with no record — the wrong trade.
Append file
+ byte-offset		 resume, not gap — reader tails from a checkpointed offset; events written while down are still on disk → replayed; producer/consumer decoupled Chosen. The only gap is genuine downtime, recorded as a NONE. Growth is already governed by retention & aging governs it.
Unix socket needs a spool to survive reader restarts True backpressure, but more parts for no NONE-honesty gain over the file.
 
LaunchDaemon (root):   eslogger exec  >>  $WORKSPACE/stream/exec.ndjson   (append; rotated)
LaunchAgent  (user):   reader tails exec.ndjson from a checkpointed byte offset
                       → on each complete line: normalize → per-event Sigma fire
                       → on an interval timer:  battery over the trailing window
                       → fsync the offset after a processed batch (the resume point)
  • Restart = resume, not gap. The checkpointed offset is the durable position; after a crash the reader seeks there. Events written while down are on disk → replayed. Only downtime that exceeds retention (the file rotated past the offset) is a real gap — recorded as a NONE, not hidden.
  • Partial lines: a line commits (and the offset advances) only on a trailing newline.
  • Rotation: the checkpoint is (file-id, byte-offset); the reader finishes the old inode, then picks up the new file at offset 0.
  • Backpressure: decoupled — if the reader lags the file grows and it catches up; eslogger never blocks. The lag (offset vs file size) is itself a feed-health signal.

6 · Intake and outflow — this doc and its pair

A continuous monitor accumulates without bound, and the source gives no help. This page is the intake; its pair, retention & aging, is the outflow — what the accumulated state folds into before it is dropped: raw events → aggregate cells + baselines → verdicts with materialized provenance, with the retention horizon recorded as a NONE boundary. The hot trailing window the battery reads here is the first stage of that lifecycle.

7 · Honest scope

  • Built: nothing here. evaluate_round and the battery are batch (list[dict] in); there is no stream reader, no daemon, no workspace store. The eslogger→OCSF adapter is the one piece that exists.
  • Smallest first step: the reader loop run by hand against a live eslogger stream — per-event Sigma firing only, no window state — to prove the intake. The launchd plists and the windowed battery come after the loop does what it should.
  • Feed-liveness wiring: the reader is where feed_live stops being hardcoded — a stalled read or a closed pipe is the NONE the temporal fold consumes.
  • The off-switch still applies per-source. The high-fidelity Windows cred-access fields (CallTrace, GrantedAccess) have no OCSF home, so a streamed source feeding fidelity-critical detections runs native, not normalized — the reader honors the same per-source vocab choice as a batch round.
One line. The source remembers nothing, so capture is the only history and a gap is an honest NONE; per-event rules stream as verifiers while the statistical battery runs as a windowed surfacer; and "continuous" is a single stateful engine process — a launchd daemon bound to a workspace, collection split from analysis by a pipe.
