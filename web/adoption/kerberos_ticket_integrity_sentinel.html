Kerberos Ticket-Integrity Detection — Microsoft Sentinel

Golden Ticket & Pass-the-Ticket via issued-vs-presented TGT hash correspondence.

design draft · KQL is a starting point to validate · Log Analytics is append-only, so the live table is approximated (summary rule) or externalized

Events 4768 (TGT issued) and 4769 (service ticket requested), in their version 2 form (Windows Server 2016+ with the 2025-01-14 cumulative update or later), log the hash of the ticket. That lets the log layer rebuild the issuance ledger the KDC deliberately does not keep, and enforce one invariant: every TGT presented in a 4769 must correspond to a TGT actually issued in a 4768.

  • Presented TGT hash that no 4768 ever issued → forged TGT (Golden Ticket).
  • Legitimately issued TGT presented from a different client context than issuance → stolen ticket reuse (Pass-the-Ticket).
Platform caveat up front. Log Analytics (Sentinel's store) is append-only and immutable — no UPDATE/DELETE, no keyed table with real TTL. So the live table is built three ways of increasing fidelity: a scheduled anti-join (windowed), a Summary Rule materializing the issued set, or true mutable state in an external store driven by a Function. (The Splunk version gets the mutable table natively via KV Store.)

1. Why it works — and the one hard assumption

Kerberos validates a presented ticket cryptographically (it decrypts under the krbtgt key and its signatures hold), not by looking it up in a registry of issued tickets. The KDC keeps no such registry — by design, for statelessness and multi-DC scale. That is exactly why a Golden Ticket works: an attacker holding the krbtgt hash forges a TGT that decrypts and validates perfectly, and the KDC has no issuance memory to contradict it.

The v2 hash fields let a centralized log platform rebuild that missing registry — stateful, bounded (only currently-valid tickets, ~10h up to ~7-day renewable), and off the request hot path: the three things the KDC could not be.

Hard assumption: the check is only as sound as 4768 collection completeness. A legitimately issued TGT whose 4768 was not collected will look forged. Issuance-log coverage is a first-class prerequisite (§7).

2. Prerequisites

  1. Patch/OS level. DCs on Windows Server 2016+ with the 2025-01-14 CU or later, emitting 4768/4769 v2. Unpatched DCs do not emit the hash fields — the detection is blind on them (fail-open; inventory them).
  2. Auditing. Audit Kerberos Authentication Service (4768) and Audit Kerberos Service Ticket Operations (4769) enabled on all DCs.
  3. Ingestion — verify first. The hash fields are new, so the connector almost certainly has no dedicated column for them yet — they land inside the raw EventData and need parsing. Confirm they arrive: 
    SecurityEvent
| where EventID in (4768, 4769)
| take 20
| project EventData
    Look for RequestTicketHash, ResponseTicketHash, ResponseTicket. With the modern AMA / WindowsEvent path plus a Data Collection Rule you can capture the full event; the legacy connector may not carry the new fields without a DCR change. If absent, fix collection before writing any detection.

Field-name reference (asymmetric — key detail)

EventMeaningTicket-hash field(s) in EventData
4768TGT issued by DCResponseTicket (the issued TGT)
4769Service ticket requested (client presents its TGT) RequestTicketHash (TGT presented) · ResponseTicketHash (service ticket issued)
The correspondence to key on: 4768.ResponseTicket ⇄ 4769.RequestTicketHash. Confirmed against Microsoft's own sample events, which show the same base64 value across a 4768→4769 pair for one session.

3. Three build tiers

TierMechanismFidelity / cost
1Scheduled analytics rule — KQL leftanti join over a window Ships today in pure KQL. Window replaces TTL; simplest. Re-scans each run.
2Summary Rule materializing the issued set into a custom table Closest KQL-native "table"; bounds cost — the check reads a small table instead of re-scanning raw events.
3External mutable store (Table Storage / Cosmos / Redis) driven by a Function/Logic App True insert/update/expire semantics. Only if the window approximation is not precise enough.

Watchlists are not the vehicle — they are for small static reference data; per-session TGT hashes churn far too hard.

4. Implementation (KQL)

Column names (TargetUserName, ServiceName, IpAddress, Computer) and the extract() patterns are illustrative — the new hash fields live in the raw EventData and must be parsed; verify against your actual schema and collection path.

4.1 Tier 1 — scheduled rule, leftanti anti-join

let win = 7d;                    // ≥ max renewable TGT life, so live TGTs aren't "missed"
let issued = SecurityEvent
  | where TimeGenerated > ago(win)
  | where EventID in (4768, 4770)                          // issuance + renewal (Defeater 1)
  | extend IssuedHash = extract(@'ResponseTicket">([^<]+)', 1, EventData)
  | project IssuedHash, IssuingDC=Computer, Account=TargetUserName,
            IssuerIp=IpAddress, IssueTime=TimeGenerated;
SecurityEvent
| where TimeGenerated > ago(1h)
| where EventID == 4769
| extend PresentedHash = extract(@'RequestTicketHash">([^<]+)', 1, EventData)
| where isnotempty(PresentedHash)
| where ServiceName !endswith "$" and ServiceName !startswith "krbtgt/"   // cross-realm cut (Defeater 2)
| summarize arg_min(TimeGenerated, *) by PresentedHash                     // distinct TGT, not per access
| join kind=leftanti issued on $left.PresentedHash == $right.IssuedHash    // presented − issued = golden
| project TimeGenerated, TargetUserName, ServiceName, PresentedHash, IpAddress, Computer

The leftanti result is the Golden-candidate set. Pass-the-ticket is the complementary inner join comparing presenting IpAddress to the origin's IssuerIp:

... | join kind=inner issued on $left.PresentedHash == $right.IssuedHash
    | where IpAddress != IssuerIp
    | project TimeGenerated, TargetUserName, ServiceName, PresentedHash,
              PresentingIp=IpAddress, IssuerIp, IssuingDC, IssueTime

4.2 Tier 2 — materialize the issued set (Summary Rule)

Roll 4768/4770 into a custom table (e.g. LiveTGT_CL) keyed by hash with the origin, refreshed on schedule; the detection then joins against that small table instead of re-scanning raw events. This bounds cost and is the closest KQL-native analogue to the Splunk KV Store table. (Confirm Summary Rule / materialized-view availability in your workspace — the feature set has evolved.)

4.3 Tier 3 — external mutable state

A Function/Logic App maintains live_tgt in Table Storage / Cosmos / Redis (insert on 4768, update on 4770, expire on TTL); Sentinel queries it or the Function alerts directly. Only warranted when the window approximation is insufficient.

5. Defeaters & tuning

A miss is only "Golden" after these clear — the false-positive sources, handled as rules rather than blind suppression.

#Legitimate causeHandling (KQL)
1Renewal — 4770 mints a new TGT hashInclude 4770 in the issued set. Without it, renewals read as Golden.
2Cross-realm — TGT issued by another realm's KDCServiceName filter for referral/machine services; for real coverage, join across realms' workspaces (Lighthouse / cross-workspace).
3Out-of-order / late logs — 4769 before its 4768Generous win plus a grace delay on the rule (query ingestion_time()); re-evaluate before firing.
4Coverage gap — DC's 4768s not collected but 4769s areNot tunable in-query — an ingestion problem. Monitor per-DC 4768 volume (§7).
5Pre-window — TGT issued before winSet win ≥ max renewable lifetime; on Tier 2, backfill the table before enabling alerting.

RC4 downgrade (TicketEncryptionType == "0x17") is a useful corroborator on a Golden candidate, not a primary signal.

6. Alert output & triage

  • Golden candidate — presented hash, account, service, presenting IP, serving DC. The absence of an issuance origin is the finding. High severity (implies krbtgt compromise / domain persistence). Map entities (Account, Host, IP) for the incident graph.
  • Pass-the-ticket candidate — presented hash with its issuance origin and the diverging presenting IP. The mismatch is the finding. High severity.

Triage: is the account/host expected? Does the presenting IP match the user's normal workstation? For Golden, first rule out a coverage false positive (serving DC is v2; that DC's 4768 coverage is healthy) before escalating.

7. Validation, testing, coverage

  • Plumbing: confirm hash fields parse out of EventData on live data before trusting any verdict.
  • Coverage health (standing): alert if a DC stops emitting 4768s while still emitting 4769s. 
    SecurityEvent
| where EventID in (4768, 4769)
| summarize count() by bin(TimeGenerated, 1h), Computer, EventID   // watch 4768 → 0 on any DC
  • Positive test (lab only): forge a Golden Ticket in an isolated lab; confirm the presented TGT produces a leftanti hit. Replay a real TGT from another host; confirm the context-divergence path fires. Never test against production Kerberos.
  • Negative test: confirm normal renewals, delegation, and cross-realm do not alert after the defeaters are in place.

8. Assumptions & limitations

  1. Detection, not prevention. By the time a Golden Ticket exists, krbtgt is compromised and the domain is owned. Response = krbtgt double-reset + IR.
  2. Coverage-bound soundness. Incomplete 4768 collection ⇒ false Golden positives. Coverage monitoring is not optional.
  3. Version-gated & fail-open. DCs without v2 events are invisible. Inventory patch level.
  4. Cross-realm needs cross-workspace. Single-workspace, the referral cut avoids false positives but does not truly validate cross-realm tickets — only excuses them.
  5. Cost. 4769 is high-cardinality (every service-ticket request). Ingesting all of it and running frequent joins has real billing impact — the summarize dedup and the Tier-2 materialized table are cost control, not just elegance.
  6. Feature currency. Summary Rules / materialized-view support on Log Analytics have evolved and differ from raw ADX — confirm what is GA in your workspace.
  7. The KQL here is a starting point — schema, parsing, and rule mechanics must be validated and adapted before production use.
