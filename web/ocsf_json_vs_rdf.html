OCSF / JSON vs RDF — not either-or, a seam

JSON at the edge, RDF at the join. Why canonmon uses both.

canon · design decision · 2026-06-05 · extends canonmon_multisource_unifier.html

If OCSF is JSON and JSON is better-tooled, why does canonmon reach for RDF at all? Because OCSF and RDF are not competitors — they solve different problems. OCSF normalizes fields ("what is a principal"); RDF supplies identity and relationships ("this principal is that one, across five sources"). canonmon needs both, and the honest move is to cross between them at one deliberate seam.

Tree vs graph — the actual difference

JSON is a tree: each event is a self-contained record, and links between events are foreign keys (IDs) you re-join later. RDF is a graph: a node is a global identifier, so the same user across host + cloud + auth logs is automatically the same node — the graph merges by identity. That merge-by-identity is canonmon's entire reason to exist (cross-source correlation = shared nodes). In JSON you write that join yourself.

The honest catch: RDF's real competitor isn't JSON — it's property graphs (Neo4j/Cypher). For graph work specifically, Neo4j has arguably better, more popular tooling than RDF, and the whole-system-provenance research field (PIDS) mostly uses property graphs for performance at scale. If canonmon's priority were production detection throughput, property-graph could win. RDF is a fit-to-canon choice, not a universal one.

Why RDF still fits canon

  • canon's priority is justification + framework-grounding + interop — not raw throughput. That is exactly RDF's strength (PROV-O, the already-RDF frameworks, standard vocabularies).
  • canon already speaks RDF — semantic-core is rdflib/SHACL/OWL, the substrate emits PROV-O, Atlas is Turtle. RDF is the existing substrate, not a new dependency.
  • content-addressing maps cleanly to IRIs / CIDs (the one-hash-three-roles keystone).

The architecture: JSON at the edge, RDF at the join

raw log  ──(SKOS bridge)──►  OCSF normalized JSON  ──(lift)──►  content-addressed RDF graph
  │                              │                                 │
  edge: parse / normalize /      the wire format                   the JOIN: cross-source merge,
  filter per-event               (tooling shines here)             provenance (PROV-O), framework query

                                          cross the boundary ONCE, deliberately, where graph questions start

Don't force every event through RDF — that's where its overhead bites and JSON's tooling is missed. Lift to the graph at the seam where the graph questions begin (the join, the lineage, the framework grounding). Same right-tool-per-joint / narrow-waist discipline canon uses everywhere: OCSF is the wire format, RDF is the graph layer, and you cross once.

The one-line answer. canonmon should use OCSF — as the JSON ingestion / normalization format — and lift to RDF at the graph / provenance / framework seam. Not "JSON or RDF" but "JSON at the edge, RDF at the join." Doing everything in JSON would mean re-solving the join, the provenance, and the framework grounding by hand — and giving up the free join to ATT&CK / D3FEND / CASE-UCO, which is half of canonmon's value.
