ATLAS-semex / KINAITICS

MITRE ATLAS rendered as a queryable OWL knowledge base — what it is, what it actually contains, and where (and where not) it fits canon.

canon · reference / scope · 2026-06-15 · revised 2026-06-16 (§8: AI-as-application-class, the join synthesis, consolidation) · verified against the live atlas-semex.ttl

A Horizon-Europe project (KINAITICS, KU Leuven / DistriNet) published the MITRE ATLAS adversarial-ML framework as an OWL/Turtle ontology you can run a description-logic reasoner over. The shape is exactly the move canon makes for the conventional-intrusion frameworks (D3FEND, ATT&CK) — a framework rendered as a logical artifact, queried for entailments a flat YAML can't answer — but in the AI-threat domain. That is the reason it's worth scoping. This page separates what is verified from what is reported but unconfirmed, then states honestly where it lands relative to the canon spine.

Naming collision — read first. Two unrelated "Atlas" live in this orbit. MITRE ATLAS = Adversarial Threat Landscape for AI Systems (attacks on ML systems) — the subject of this page. Canon's ~/atlas = your standalone SKOS/RDF library of analytical primitives (information theory, detection theory) — a completely different thing. They share a word and nothing else. Do not let any downstream reader conflate them.

1 · What it is — the artifact

Source paper: Preuveneers, D.; Joosen, W., "An Ontology-Based Cybersecurity Framework for AI-Enabled Systems and Applications," Future Internet 2024, 16(3), 69. Authors are DistriNet, KU Leuven; the work is positioned under the KINAITICS project. Paper, authors, journal, and project all verified.

The generated knowledge bases are hosted under the author's namespace people.cs.kuleuven.be/~davy.preuveneers/ns/cti/:

FileDomainStatus

atlas-attack-semex-enterprise.ttlMITRE ATT&CK Enterprise (companion)verified — exists; ATT&CK spec 3.1.0; large
Correction to the secondhand account. The summary that prompted this scope listed files atlas-semex.ttl / attack-semex.ttl / .rdf variants and an "OASIS Threat Actor Context (TAC) ontology" base. Checked against the live file: atlas-semex.ttl is real; the ATT&CK companion is actually named atlas-attack-semex-enterprise.ttl, not attack-semex.ttl; and there is no tac: namespace in the published Turtle — it imports stix-semex and attack-semex, not a TAC ontology. The TAC claim is either from an earlier draft or wrong. Treat the "v4.5.1 mapping", "HermiT/ELK", "Manchester-syntax queries" and "Spring Boot PoC" specifics as reported-from-the-paper, not independently confirmed.

2 · What the ontology actually contains

This is the load-bearing technical fact, and it's not what the prose summary implies. ATLAS-semex is STIX 2.1 reified into OWL named individuals — not a hand-built domain TBox of rich class restrictions. The ontology header imports the STIX-as-OWL base and the ATT&CK extension, then lists every ATLAS object as an owl:NamedIndividual typed with a STIX class:

# ontology header — verified verbatim
<…/atlas-semex> rdf:type owl:Ontology ;
    owl:imports <…/ns/cti/stix-semex> ,
                <…/ns/cti/attack-semex> .

# one ATLAS technique, as it actually appears
:attack-pattern--92c8… rdf:type owl:NamedIndividual , stix:AttackPattern ;
    cti:name "Search for Victim's Publicly Available Research Materials" ;
    cti:description """Adversaries may search publicly available research…""" ;
    stix:kill_chain_phases :kill_chain_phases--c8ad… ;     # → tactic
    cti:external_references :external_reference--8474… ;   # → AML.Txxxx id
    attack-semex:x_mitre_platforms "ATLAS" .

Verified class distribution across the 666 named individuals:

STIX classCountATLAS meaning
stix:AttackPattern82techniques (incl. sub-techniques)
attack-semex:Tactic14tactics
stix:CourseOfAction20mitigations
stix:Relationship107technique↔tactic↔mitigation links

cti:ExternalReference117AML ids, citations
attack-semex:Matrix / Collection1 / 1the ATLAS matrix bundle
Where the query power actually lives. Because the techniques are thin STIX individuals, the DL-reasoning leverage comes from the 107 Relationship objects + kill-chain phases and from the class/property axioms in the imported stix-semex / attack-semex TBoxes — not from deep restrictions on the techniques themselves. The reported queries ("which mitigation is circumvented by which technique") are reachable if those relationship objects carry the mitigates/revoked-by edges; the modality query ("image-vs-tabular models") is unconfirmed — I saw no modality datatype property in the sample, only x_mitre_platforms "ATLAS".
This is the ABox/TBox distinction you already documented. Canon's d3fend_tbox_vs_log_abox page draws exactly this line. D3FEND is a rich TBox (OWL restrictions: "T1003.001 accesses a Process") that canon reasons over for defensive-offensive artifact joins. ATLAS-semex is mostly ABox — STIX instances with relationship edges. Same serialization (OWL/Turtle), very different reasoning depth. Any canon integration must treat them differently: D3FEND earns subsumption entailments; ATLAS-semex earns graph-relationship traversal.

3 · Why this matches what you were imagining

The architectural pattern is one-for-one with canon's existing semantic-cyber stance, transposed to the AI-threat domain:

  • Framework → logical artifact. A flat MITRE YAML becomes an OWL graph a reasoner can answer entailment questions over — the same reason canon loads D3FEND as 45K triples instead of calling an API.
  • Reasoner as the deductive verifier. A DL reasoner (HermiT/ELK, reported) in the verifier seat is precisely the role canon assigns to deduction in the abduction loop: the sound check, no LLM, returns entailment or nothing.
  • Cross-framework join, built in. atlas-semex imports attack-semex and reuses its x_mitre_* vocabulary — so ATLAS and ATT&CK techniques live in one federated namespace, queryable together. That is the W→route join idea, already wired for the AI side.

So the instinct is right that this resembles the canon design — but resemblance is at the methodology level (how you render and query a framework), not at the content level. The content is a different threat universe, and that distinction is the whole scope question.

The cheapest concrete move: add atlas-semex.ttl as a third corpus in semantic-cyber, next to D3FEND and ATT&CK. It already imports the attack-semex namespace canon would also be loading, so a federated "ATLAS technique ↔ ATT&CK technique ↔ D3FEND countermeasure" query is a small, demonstrable artifact. That alone is a real capability: navigate AI-threat TTPs against the conventional defensive graph.

5 · Where it does NOT fit — caveats that bound the value

  • Different threat domain — canon has zero detectors here. The detection battery (Kerberos fan-out, CloudTrail, off-hours, coordination) surfaces conventional intrusion telemetry. MITRE ATLAS is adversarial ML: evasion, poisoning, model extraction, prompt injection. There is no telemetry detector in canon that grounds an ATLAS technique. So this is a semantic corpus you can query, not a corpus the battery verifies against. Treating it as the latter would over-claim.
  • The published artifact is stale. The individuals are dated 2024-01-12 → an early-2024 ATLAS snapshot: 82 techniques / 14 tactics / 20 mitigations. Current ATLAS is v5.1.0 (Nov 2025): 16 tactics, 84 techniques, 56 sub-techniques, 32 mitigations, 42 case studies (per MITRE). The entire Spring-2025 GenAI/LLM expansion — RAG poisoning, prompt-injection, AI supply-chain — is absent from the .ttl. The mapping pipeline is reusable; the shipped graph is ~18 months behind.
  • No case studies as individuals. ATLAS's 42 real-world case studies are arguably its richest content; I found no stix:Report/sighting objects carrying them in the .ttl. The graph is TTP-structure, not incident-grounded.
  • ABox-shallow reasoning. Per §2 — don't expect D3FEND-grade artifact-restriction entailments. The reasoning is relationship traversal over STIX instances.
  • Epistemic stance still binds. Per the guarantees ledger — frameworks are validatable hypotheses; bedrock is logic + empirical reality. A reasoner returns the deductive consequences of what the ontology asserts; ATLAS-semex asserts, it does not validate. It is a hypothesis graph to query, not ground truth.

6 · What canon could actually do with it — options, scoped

  1. Reference / methodology study (smallest). Read the .ttl as a worked example of STIX→OWL framework rendering. Value: confirms canon's approach; costs ~nothing. Recommended baseline.
  2. Third semantic-cyber corpus (small, demonstrable). Ingest atlas-semex.ttl, federate with ATT&CK/D3FEND, ship one cross-framework query (AI TTP → enterprise technique → countermeasure). Value: a real capability, honestly an AI-threat navigation tool, not detection. Recommended if you want a concrete artifact.
  3. Re-mint from current ATLAS (medium). The shipped graph is stale; canon could run its own YAML/STIX→OWL pass against ATLAS v5.1.0 to get the GenAI techniques. Only worth it if option 2 proves useful.
  4. Open an adversarial-ML detection front (large — a program decision). Build actual detectors for ATLAS techniques (e.g. model-extraction query patterns, poisoning signals) and wire ATLAS-semex as their verifier framework, mirroring the battery↔framework inversion. This is a new threat domain for canon, not an afternoon. Flag it as such; don't drift into it by accident.
Recommendation. File this as methodology reference + candidate 3rd corpus, not "the AI version of canon." The pattern-match to your vision is real and worth capturing — but the value is in the rendering/querying methodology (which canon already independently has) and in optional AI-threat navigation. Calling it "everything I imagined, in AI" is true for the architecture and false for the content: canon's edge is empirically-grounded, self-validating detection, and this artifact is an asserted, un-grounded, stale TTP catalog. The honest framing is the load-bearing one.

8 · Revised view — canon, 2026-06-16

After working the join model and the threat-domain question, three refinements to §4–6.

AI is an application class, not a parallel domain

MITRE ATLAS isn't a universe beside traditional cyber — it's a new application class layered on conventional infrastructure (as web-apps + OWASP sit on infra + ATT&CK). AI attack chains compose with conventional ones: poison a model → first breach the training data-store (ATT&CK), then poison (ATLAS); extract a model → API cred-access (ATT&CK), then extraction queries (ATLAS). That is why atlas-semex imports attack-semex — the ontology federates them because the threats do. So canon is not zero-relevant here: it already grounds the conventional rungs of an AI kill chain; the gap is the model-layer rungs.

ATLAS tacticcanon coverage
Reconnaissance · Resource Developmentnone — OSINT / attacker-side, not victim telemetry
Initial Access · Execution · Persistence · Priv-Esc · Defense-Evasion · Credential-Access · DiscoveryCOVERED — these are the ATT&CK rungs canon's detectors fire on (enumeration→discovery, account-manip→priv-esc, region-sweep→impact)
ML Model Access · Collection · Exfiltration · ImpactPARTIAL — the cyber half is covered (API auth, data access, cyber-exfil, cost/DoS); the model half is gap
ML Attack Staging (poison / craft / backdoor) · model-evasion · inference-API extractionGAP — model-layer telemetry canon doesn't have

canon owns the conventional middle of the AI kill chain today; the AI-specific bookends + staging are a telemetry gap, not a whole new framework universe. ATLAS-as-corpus's real use is to mark exactly where canon's coverage ends and the model-layer begins.

The join model — code-join vs graph-join

Checked semantic-cyber/bridge.py directly: no SKOS pairwise mappings — it already federates by a shared key (the ATT&CK technique id), folding D3FEND + ATT&CK + Sigma + UKC into a provenance-tracked coverage report. So canon does code-join; KINAITICS does graph-join (one RDF graph, owl:imports, reasoner federates). They trade exactly against each other:

dimensioncanon (code-join)KINAITICS (graph-join)
new frameworka bridge fn per fwowl:imports + shared vocab, no code
cross-framework entailmentonly what's codedreasoner derives multi-hop free
speedfast (lookup)slow (DL reasoner)
provenance of the joinexplicit (PROV-O)not inherent
discriminationreasons only where it pays (D3FEND TBox)reasons over everything

Keep both — "graph substrate, code-join hot path, reasoner on demand": a shared upper vocab (STIX/UCO) so frameworks federate by IRI (cheap federation); the fast provenance-tracked join stays in the detection hot path (speed + grounding); the reasoner is an opt-in layer for entailment queries (navigation/analyst), never in the hot path.

Consolidation intent. The goal is to consolidate cyber knowledge in the best structure — rich + a flexible mechanism to consume more (comprehensive ≠ complete). That structure is the shared-upper-vocab (STIX/UCO) substrate above: an open-world graph you keep adding frameworks to (ATLAS, OCSF, CAPEC, CWE, CVE, Engage, NIST…), never a fixed schema to finish. It is the natural home for vulnerability specifically — vuln chains by its own ids (CVE→CWE→CAPEC→ATT&CK), which shared-IRI federation handles where an ATT&CK-id code-join would not. The core already supports this (graph-load + reasoning + SHACL + PROV-O lineage); the guardrail to keep the path open is just: keep frameworks loadable as graphs and don't hard-code the ATT&CK technique-id as a universal join key (canon already complies). Harden the core now; the shared-vocab federation is the layer the core grows into, not a rewrite.
Revised recommendation. Still: methodology reference + candidate navigation corpus, gated on license + whether the Relationship edges carry mitigates/circumvents semantics. But the AI-as-application-class reframe upgrades the framing — canon is partially relevant to AI threats today (it grounds the conventional rungs of the AI kill chain); ATLAS's value is to mark where that coverage meets the model-layer gap. The corpus pays off most once the shared-vocab federation exists — which is itself the consolidation layer the core is being hardened to grow into.
