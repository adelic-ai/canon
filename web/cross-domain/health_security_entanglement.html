Health × security: entangled, not core

Two readings of one telemetry stream. Consume it, emit the byproduct — don't become an observability platform.

canon · design conversation · 2026-06-12 · companion to completeness_channel.html · scope note

A routinely-missing field is a critical problem — and not only for the SOC. Security and system health run on the same telemetry, so a persistent gap is a defect in a shared asset. This panel names the entanglement honestly, and then draws the boundary that keeps canon detection-first.

Entangled, not just adjacent

"Adjacent" undersells it. Security and health are entangled in three concrete ways:

  1. Shared telemetry. The same events feed detection and performance monitoring, capacity planning, debugging, compliance. (OCSF and OpenTelemetry are converging precisely because the field/event vocabulary serves both.)
  2. Shared math. canon's battery is modality-agnostic — a CUSUM on request latency is the same primitive as a CUSUM on auth volume; KL on service-error distributions is the same as on credential fan-out. The anomaly layer doesn't know which it's watching.
  3. Shared anomalies. A service crash, a disk filling, a latency spike are health signals that are sometimes also security signals (a crash can be an exploit; a disk filling can be exfil staging). The signal spaces overlap.

They diverge in only two places: interpretation (bug or adversary?) and owner (SRE or SOC?). And the disambiguation is the validity fold's same three causes — innocent / pipeline / attack — resolved the same way (correlation, held NONE until evidence breaks the tie). So it is not two adjacent domains; it is two interpretations of one system-state stream, splitting only at triage.

Necessity is consumer-relative

The completeness channel split fields into "necessary / not-necessary for this finding." Widen the lens and the same field is necessary for a different consumer: a field the SOC correctly drops as detection-irrelevant may be exactly what the SRE team needs for capacity planning or the billing team needs for chargeback. So the "not-necessary" bucket isn't garbage — it's another team's load-bearing signal. That's why those gaps are carried and routed, never dropped.

The dependency is asymmetric: health → security

Security's observability is a function of system health. Degraded telemetry health directly produces security blind spots — you cannot detect what the pipeline dropped. So poor health isn't merely adjacent to a security problem; it manufactures security problems: every persistent gap widens the NONE frontier. Health → security, more than the reverse.

The byproduct — honest detection emits a health signal

Here is the part that keeps this from being scope creep. canon must track telemetry completeness to be truthful about NONE — and that tracking is a telemetry-quality artifact the infra team wants ("forwarder X drops 3% of EID1 fields; sensor on DC-01 stopped populating GrantedAccess Tuesday"). So canon generates an infra-health product as a side effect of being epistemically honest about its own gaps — same pattern as the regime-ledger emitting learning signal as a byproduct. Do the honest thing; a valuable secondary artifact falls out, with a different customer.

Stance: forensic instrument over telemetry. At the substrate level, health and security are one forensic problem — reconstruct what happened from incomplete evidence, honestly. They split only at interpretation/triage. So: consume health where it bears on security (the observability gate, the completeness channel), emit the health byproduct to its owners, but don't try to be an SRE platform. Recognize the entanglement; don't dissolve into it.

Where this sits — core vs adjacent vs parked

This panel exists to be remembered and bounded. The current focus is detection and the core; the entangled things are acknowledged, not forgotten, not chased.

bandwhat
CORE — focus now the detection logic + detection structure · entry points · the relational provenance graph (how nodes relate — PROV entities/activities + used / wasGeneratedBy / wasInformedBy edges; the substrate backbone you reason over).
ADJACENT — consume / emit, not core system health (this panel — byproduct + observability gate) · source-custody provenance (signed logs, in-toto/DSSE, "from Splunk vs direct Sysmon"). Note: custody is honest-NONE on all current/unsigned data anyway — inert until signing is wired, so deprioritizing it now costs nothing.
PARKED — future-important detection availability / path orchestration — organizing when logs are available and through what path they arrive, and structuring detection around that. Distinct from both entry points and detection logic; the plumbing/timing substrate under detection. Reason about it later.
The two meanings of "provenance" — don't conflate them. Relational provenance (the PROV-O graph of how nodes relate) is core — it's the structure detection reasons over. Custody / source provenance (signing, where-from) is adjacent and deprioritized now. Same word, different layers: one is the structure itself, the other is trust in the source of the structure.
